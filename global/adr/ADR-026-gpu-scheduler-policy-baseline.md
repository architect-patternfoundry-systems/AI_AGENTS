# ADR-026: GPU Scheduler Policy Selection and Load Characterization Baseline

**Status**: Accepted  
**Date**: 2026-07-07  
**Deciders**: Platform Team  
**Supersedes**: Passive "Week 4 production data collection" posture (chapter 21–25, `gpu_scheduler_journey/`)

**Version pins**:
- Harness version: `1.1.0`
- Baseline artifacts: `gpu_scheduler_simulator/results/exp1_load_ladder_sweep.json`, `exp1_slo_status.json` (generated by harness v1.1.0)
- Telemetry schema: TELEMETRY_SPEC.md v1.0

## Context

The GPU scheduler roadmap (`GPU_SCHEDULER_READINESS_GATE.md`) required a decision on:

1. Which scheduling policy to deploy as the production baseline
2. Under what load conditions a second GPU (RG-01) is justified
3. How sensitive the Interactive SLO (<30s mean wait) is to real hardware preemption cost

The original plan called for "7–10 days of production data collection" before making these decisions. This environment is dev/pre-prod with no organic load, making passive collection a non-starter. The approach was replaced by a **controlled load characterization apparatus** that produces the same decision artifacts via structured simulation at defined operating points.

---

## Decision

**Deploy `EventAffinity+Credit+Preemption` as the production scheduling policy.**

This decision is based on empirical data from the load characterization harness
(`gpu_scheduler_simulator/load_characterization_harness.py`, v1.1.0).

All results use 20 seeds per configuration, 600s simulation horizon, empirically calibrated parameters.

### Experiment 1: Load ladder (5 levels × 3 profiles × 6 policies)

Key finding: the two preemption-enabled policies are the only ones that hold the Interactive SLO across all load levels and job mix profiles. `EventAffinity+Credit+Preemption` is selected over `EventAffinity+Preemption` because credit aging prevents starvation under sustained load (lower max-wait at L3/L4). All non-preemption policies begin breaching at L2 under the batch-heavy calibration profiles.

| Policy | L2 balanced SLO | L3 balanced SLO | L4 balanced SLO |
|--------|----------------|----------------|----------------|
| EventAffinity+Credit+Preemption | ✅ 0% breach | ✅ 0% breach | ✅ 0% breach |
| EventAffinity+Preemption | ✅ 0% breach | ✅ 0% breach | ✅ 0% breach |
| EventAffinity+Credit | ❌ ~85% breach | ❌ ~85% breach | ❌ ~95% breach |
| EventAffinity | ❌ ~85% breach | ❌ ~85% breach | ❌ ~95% breach |
| AffinityWindow | ❌ ~85% breach | ❌ ~85% breach | ❌ ~100% breach |
| FIFO | ❌ ~95% breach | ❌ ~100% breach | ❌ ~100% breach |

**Note on "balanced" profile**: The `balanced` profile (33% Interactive / 50% Batch / 17% Background) is **intentionally batch-heavy** — a scheduler stress test designed to exercise worst-case starvation, not a representation of confirmed production traffic. The `ui_heavy` profile (60% Interactive) is the better proxy for expected creative/interactive workloads. This stress calibration confirms that **preemption is a required capability**: even under more Interactive-skewed workloads, the absence of preemption causes SLO breaches under moderate burst load. Once real request logs are available, `BASE_ARRIVAL_RATES` should be recalibrated against observed ratios and Exp 1 re-run.

### Experiment 3: Preemption cost sensitivity

Empirically measured preemption cost: **2.38s mean, 3.79s P95** (P0 measurement track, chapter 10).  
Production config uses **3.0s** (P95 with safety margin).

Safe hardware preemption cost range:
- **L2 (baseline)**: 1.0–5.0s — SLO met across full sweep
- **L3 (1.5x load)**: 1.0–5.0s — SLO met across full sweep  
- **L4 (2.0x stress)**: 1.0–3.5s — **breaches at ≥4.0s**

**Margin**: Measured 2.38s mean sits **1.12s (47%) below** the L4 breach threshold of 3.5s. The system is robust to hardware cost drift at all expected operating points.

### Experiment 4: Policy degradation cliff

Load at which SLO breach rate reaches ≥50% (worst-case profile):

| Policy | Fails at (worst-case) | Headroom vs L2 |
|--------|-----------------------|----------------|
| EventAffinity+Credit+Preemption | **2.0x** | +1.0x |
| EventAffinity+Preemption | 2.0x | +1.0x |
| EventAffinity+Credit | 0.8x | -0.2x |
| AffinityWindow | 0.8x | -0.2x |
| FIFO | **0.6x** | -0.4x |

FIFO fails the SLO **below baseline load** — it is not viable for this workload.

### Experiment 5: Model mix sensitivity

Swap count increase from 30% → 100% ace-step Batch fraction: **< 15%** across all policies.  
**Decision**: Affinity tuning for model mix is deferred. The scheduler is not sensitive to ace-step fraction at current load levels.

## RG-01 Multi-GPU Readiness Gate

**RG-01 is NOT triggered** under balanced or ui-heavy profiles at any load level.

RG-01 was triggered **only under `ingest_heavy` at L3/L4** — a workload profile dominated by bulk ace-step Batch jobs (60% Batch, 30% Background). This represents a distinct operating mode (bulk ingest pipeline), not the expected interactive/creative use pattern.

**Promotion criteria remain unchanged** (from `GPU_SCHEDULER_READINESS_GATE.md`):
- Interactive mean wait >25s for 3+ consecutive measurement periods, OR
- Sustained load confirmed at >1.5x baseline with ingest-heavy profile

## Consequences

### Positive
- Policy decision is grounded in 11,760 simulation runs across 5 experiments, not intuition
- SLO compliance envelope is documented and reproducible — any parameter change can be re-characterised in <10 seconds
- RG-01 condition is now precisely defined: triggered only under bulk-ingest-dominant load at 1.5x baseline
- Preemption cost sensitivity band provides a hardware procurement constraint: GPU preemption latency must remain <3.5s at stress load

### Negative / Tradeoffs
- "Balanced" profile (50% Batch) may not accurately reflect actual user workload distribution — this remains an open calibration question. If real usage is more interactive, the headroom is even larger; if more batch-heavy, re-run Exp 1 with adjusted `BASE_ARRIVAL_RATES`
- Simulation assumes independent Poisson arrivals; bursty correlated arrivals (e.g., multiple users triggering simultaneous renders) are characterised separately in Experiment 2

### Open questions
1. What is the actual Interactive:Batch:Background ratio in production? (Calibrate `BASE_ARRIVAL_RATES` once real request logs are available)
2. Does preemption cost remain stable under sustained load, or does GPU thermal state introduce drift?
3. At what point does model swap cost between large models (ace-step → image) become worth measuring per-pair? (Deferred per Exp 5)

## Re-baselining Protocol

To update this baseline after any parameter change:

```bash
cd gpu_scheduler_simulator/
python3 load_characterization_harness.py --out results/ --compact --slo-check
python3 baseline_report.py --results results/ --out results/
```

Then commit the updated `results/baseline_table.md`, `results/slo_envelope.md`, and `results/exp1_slo_status.json` alongside any parameter change. The `_compact.json` files are diff-friendly for PR review.
